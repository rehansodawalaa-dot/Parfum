# Requirements Document

## Introduction

This document defines the requirements for enhancing the J Raph Streach perfume e-commerce website. The existing site has a React 19 + Vite frontend (Zustand, TanStack Query, Tailwind CSS) and a Node.js/Express/MongoDB backend. Several customer-facing features are either missing or incomplete: wishlist, order tracking, country/currency selector, live chat, data saver mode, user-submitted reviews, and informational pages (FAQ, Contact, Shipping & Returns). This enhancement also introduces a premium luxury visual redesign, search improvements, recently viewed products, related products, newsletter subscription, and trust/payment badges.

---

## Glossary

- **System**: The J Raph Streach e-commerce web application (frontend + backend).
- **Frontend**: The React 19/Vite single-page application served to the browser.
- **Backend**: The Node.js/Express REST API connected to MongoDB.
- **Auth_Store**: The Zustand auth store (`authStore.js`) managing user session and JWT token.
- **Cart_Store**: The Zustand cart store (`cartStore.js`) managing shopping cart state.
- **Wishlist_Store**: The new Zustand store that manages the customer's saved/favourited products, persisted as `jrs-wishlist` in localStorage.
- **Data_Saver_Store**: The new Zustand store that persists the data saver preference, persisted as `jrs-data-saver` in localStorage.
- **Country_Store**: The new Zustand store that persists the selected country and currency, persisted as `jrs-country` in localStorage.
- **Review**: A customer-submitted star rating (1–5) with optional text and optional image(s) attached to a product.
- **Navbar**: The top navigation bar component (`Navbar.jsx`).
- **Footer**: The bottom footer component (`Footer.jsx`).
- **ProductCard**: The product card component (`ProductCard.jsx`).
- **ProductDetail**: The product detail page (`ProductDetail.jsx`).
- **Account**: The authenticated account dashboard page (`Account.jsx`).
- **Customer**: An end-user (logged-in or guest) browsing the site.
- **Authenticated_User**: A customer who has completed login (Auth_Store `isAuthenticated === true`).
- **Guest**: A customer who is not logged in (`isAuthenticated === false`).
- **Order_ID**: The human-readable order identifier matching the format `JRS-YYYYMMDD-XXXXX` as generated by the backend `Order` model.
- **Cart_Item**: A single entry in the cart comprising a product reference, selected size, and quantity.
- **Wishlist_Item**: A product object saved to the Wishlist_Store.
- **Data_Saver_Mode**: A site-wide toggle that reduces image quality and disables non-essential animations.
- **Country_Selector**: A UI control in the Navbar that allows the customer to choose their country and preferred currency.
- **Live_Chat_Widget**: A floating customer support chat widget visible site-wide.
- **Trust_Badge**: A small icon+label element communicating security, authenticity, or policy guarantees using Lucide React icons.
- **Newsletter**: An email subscription service for promotional updates.
- **Luxury_Theme**: The visual design system using Soft Black (`#121212`), Rose Gold (`#B76E79`), Ivory White (`#F8F4EE`), and Luxury Gold Accents (`#D4AF37`).

## Requirements

### Requirement 1: Wishlist Feature

**User Story:** As a Customer, I want to save perfumes to a wishlist so that I can easily return to products I am interested in without having to search again.

#### Acceptance Criteria

1. THE Wishlist_Store SHALL persist wishlist items in localStorage under the key `jrs-wishlist` across page reloads using Zustand's `persist` middleware, such that items survive a full browser refresh.
2. WHEN a Customer clicks the heart icon on a ProductCard or ProductDetail page for a product not already in the wishlist, THE Wishlist_Store SHALL add that product object to the items array.
3. WHEN a Customer clicks the heart icon on a ProductCard or ProductDetail page for a product already in the wishlist, THE Wishlist_Store SHALL remove that product from the items array.
4. IF a product's ID is present in the Wishlist_Store items array, THEN THE ProductCard and ProductDetail heart icon SHALL render in a filled/rose-gold (`#B76E79`) state; otherwise it SHALL render in an unfilled/outline state.
5. THE System SHALL provide a `/wishlist` route that renders a dedicated Wishlist page listing all saved Wishlist_Items as ProductCard components.
6. WHEN a Customer clicks "Move to Cart" on a Wishlist_Item, THE System SHALL call `Cart_Store.addItem(product, product.sizes[product.sizes.length - 1])` and then remove the product from Wishlist_Store, such that the item no longer appears on the Wishlist page.
7. WHEN a Customer clicks "Remove" on a Wishlist_Item on the Wishlist page, THE Wishlist_Store SHALL remove that product from the items array and the item SHALL no longer be rendered on the page.
8. IF the Wishlist_Store items array is empty, THEN THE Wishlist page SHALL display an empty-state message containing a `<Link>` to `/shop`.
9. THE Navbar SHALL display a heart icon (`Heart` from Lucide React) with a count badge showing the number of items in Wishlist_Store, updating reactively; when count exceeds 9 the badge SHALL display "9+".

### Requirement 2: Order Tracking

**User Story:** As a Customer, I want to track my order by entering an Order ID so that I know where my package is and when it will arrive.

#### Acceptance Criteria

1. THE System SHALL provide a public `/track-order` route accessible without authentication to both Guest and Authenticated_User.
2. WHEN a Customer submits a string matching the pattern `JRS-YYYYMMDD-XXXXX` on the Track Order page, THE Backend SHALL return: `orderNumber`, `status`, `carrier`, `trackingNumber`, `estimatedDelivery`, and a `statusHistory` array of `{ status, timestamp }` objects for that order.
3. WHEN a Customer submits a string that does not match any order in the database, THE System SHALL display the message "Order not found. Please check your Order ID and try again." without any stack trace or internal error detail.
4. THE System SHALL display the `status` field as exactly one of the labels: Pending, Confirmed, Processing, Shipped, Delivered, Cancelled, or Refunded, mapping directly to the Order model's status enum values.
5. WHEN the `status` field is "shipped", THE System SHALL display the `carrier` and `trackingNumber` fields returned by the backend; WHEN the status is any other value, THE System SHALL not render those fields.
6. THE Navbar SHALL include a "Track Order" link that navigates to `/track-order` in both the desktop navigation links array and the mobile drawer menu.
7. THE Footer SHALL include a "Track Order" link that navigates to `/track-order` in the Help links section.
8. WHEN an Authenticated_User navigates to `/track-order` and their order history contains at least one order, THE System SHALL pre-populate the Order ID input field with the `orderNumber` of the most recently created order (highest `createdAt` timestamp).
9. IF the Backend returns an HTTP 4xx or 5xx error for a track-order request, THEN THE System SHALL display the message "Something went wrong. Please try again." and a "Retry" button that re-submits the same Order ID.

### Requirement 3: Country and Currency Selector

**User Story:** As a Customer, I want to select my country so that I see prices in my local currency and know whether shipping is available to my location.

#### Acceptance Criteria

1. THE Country_Store SHALL persist the `countryCode` and `currencyCode` fields in localStorage under the key `jrs-country` using Zustand's `persist` middleware.
2. THE Navbar SHALL display a Country_Selector button showing the currently selected country's emoji flag and name; clicking the button SHALL open a dropdown listing all supported countries.
3. WHEN a Customer selects a country from the Country_Selector dropdown, THE Country_Store `countryCode` and `currencyCode` SHALL update immediately and the dropdown SHALL close.
4. WHEN the Country_Store `currencyCode` changes, THE System SHALL display all product prices formatted using the corresponding currency symbol and static exchange rate defined in the Country_Store configuration object (e.g., 1 INR → 0.012 USD); prices SHALL update without a page reload.
5. THE System SHALL support exactly the following five entries in the Country_Store configuration: India (`IN`, `INR`, symbol `₹`), United States (`US`, `USD`, symbol `$`), United Kingdom (`GB`, `GBP`, symbol `£`), United Arab Emirates (`AE`, `AED`, symbol `د.إ`), Singapore (`SG`, `SGD`, symbol `S$`).
6. WHEN a Customer selects United States, United Kingdom, Singapore, or United Arab Emirates (any non-India country), THE System SHALL display a banner reading "International shipping available — rates calculated at checkout" on the ProductDetail page and the Checkout page.
7. IF no `jrs-country` key exists in localStorage on first visit, THEN THE Country_Store SHALL initialise with `countryCode: "IN"` and `currencyCode: "INR"`.
8. THE Country_Selector dropdown trigger button SHALL have `aria-haspopup="listbox"` and `aria-expanded` set to `"true"` when open and `"false"` when closed; each country option SHALL have `role="option"`.

### Requirement 4: User-Submitted Product Reviews

**User Story:** As a Customer, I want to read and write product reviews so that I can make informed purchasing decisions and help other customers.

#### Acceptance Criteria

1. THE Backend SHALL provide a `Review` Mongoose model with the following fields: `product` (ObjectId ref `Product`, required), `user` (ObjectId ref `User`, required), `rating` (integer, min 1, max 5, required), `text` (String, maxlength 1000, minlength 1, optional), `images` (Array of Strings, maxlength 3, optional), `createdAt` (Date, default `Date.now`).
2. WHEN an Authenticated_User submits a review for a product, THE Backend SHALL persist the Review document and, within the same database operation, atomically recalculate and update the Product document's `rating` (weighted average) and `reviewCount` (integer count) fields; IF the database operation fails, THE Backend SHALL return HTTP 500 and SHALL NOT persist a partial state.
3. IF a Guest attempts to submit a review, THEN THE System SHALL redirect to `/login?returnTo=/product/[slug]` so the customer is returned to the product page after login.
4. THE ProductDetail reviews tab SHALL display a section heading "Reviews from Customers" (H2 or equivalent semantic heading level).
5. THE ProductDetail reviews tab SHALL display the text "Help the next customer by sharing your experience." as a paragraph directly beneath the "Reviews from Customers" heading.
6. WHEN the product has one or more Review documents, THE System SHALL render each review displaying: reviewer's first name and last initial, star rating (filled stars matching `rating`), `createdAt` formatted as "Month YYYY", `text`, and any `images` as thumbnail `<img>` elements.
7. IF the product has zero Review documents, THEN THE System SHALL display "No reviews yet. Be the first to share your experience." in place of the review list.
8. IF an Authenticated_User has not yet submitted a review for the current product, THEN THE System SHALL display a review submission form containing: a 1–5 interactive star selector, a `<textarea>` (maxlength 1000), and a file `<input>` accepting `image/jpeg,image/png,image/webp` with `multiple` up to 3 files.
9. IF an Authenticated_User has already submitted a review for the current product, THEN THE System SHALL display that review's existing `rating`, `text`, and `images` pre-populated in the form fields alongside an "Update Review" submit button and a "Delete Review" button, replacing the standard submission form.
10. THE Backend SHALL enforce a unique compound index on `{ product, user }` in the Review model such that a second `POST` review for the same product by the same user returns HTTP 409 with the message "You have already reviewed this product."
11. WHEN review images are submitted, THE Backend SHALL validate that each file's `Content-Type` is one of `image/jpeg`, `image/png`, or `image/webp` AND that each file size does not exceed 5,242,880 bytes (5 MB); IF any file fails validation, THE Backend SHALL return HTTP 400 with a message specifying which file failed and the reason (invalid type or size exceeded).
12. THE Backend SHALL return HTTP 409 with the body `{ message: "You have already reviewed this product." }` when a duplicate review submission is detected, and THE Frontend SHALL display this message to the user without resetting the form fields.
13. THE System SHALL display reviews ordered by `createdAt` descending (newest first) by default.

### Requirement 5: Data Saver Mode

**User Story:** As a Customer on a slow or limited internet connection, I want to enable Data Saver Mode so that the website loads faster and uses less data.

#### Acceptance Criteria

1. THE Data_Saver_Store SHALL persist the data saver preference as a boolean field `enabled` in localStorage under the key `jrs-data-saver` using Zustand's `persist` middleware.
2. THE System SHALL provide a Data Saver toggle control in the Footer settings area, labelled "Data Saver".
3. WHEN Data_Saver_Mode is enabled, THE Frontend SHALL append `?auto=compress&cs=tinysrgb&w=400` to all Pexels CDN image `src` URLs instead of the full-resolution `w=800` variant, applying to all `<img>` tags site-wide.
4. WHEN Data_Saver_Mode is enabled, THE Frontend SHALL suppress the following named animations and transitions: `PageTransition` component fade-up, `CursorGlow` component, `Reveal` component IntersectionObserver reveals, `useSlideIn` hook transitions, ProductCard hover scale/overlay transitions, and `.marquee-track` animation; the `prefers-reduced-motion` media query CSS block already present in `index.css` SHALL serve as the implementation pattern.
5. WHEN Data_Saver_Mode is disabled, THE Frontend SHALL use full-resolution image URLs (`w=800`) and SHALL enable all animations listed in criterion 4.
6. WHEN a Customer toggles the Data Saver control, THE `Data_Saver_Store.enabled` value SHALL update within the same render cycle (i.e., the React re-render triggered by the store update SHALL reflect the new state before the next browser paint), without any page navigation or reload.
7. THE Data Saver toggle SHALL render as a `<button role="switch">` with `aria-checked="true"` when enabled and `aria-checked="false"` when disabled; the button SHALL be reachable via Tab key and SHALL have a visible focus outline; an adjacent text label SHALL display either "ON" or "OFF" matching the current state.
8. IF no `jrs-data-saver` key exists in localStorage on first visit, THEN the `Data_Saver_Store.enabled` field SHALL initialise to `false`.

### Requirement 6: Live Chat Support Widget

**User Story:** As a Customer, I want to contact support through a chat widget so that I can get quick answers to my questions without leaving the site.

#### Acceptance Criteria

1. THE Live_Chat_Widget SHALL be rendered as a floating `<button>` with `position: fixed; bottom: 1.5rem; right: 1.5rem` on every page whose pathname is NOT `/login` or `/signup`; the button SHALL use `z-index: 9998` (below the Navbar z-50).
2. THE Live_Chat_Widget panel header SHALL render the text "Chat With Us" as its visible heading when the panel is open.
3. WHEN the Live_Chat_Widget is opened for the first time in a session (panel rendered for the first time), THE System SHALL display the message "Have any questions? We're happy to help." above the pre-chat form fields.
4. THE Live_Chat_Widget SHALL present a pre-chat form with the following fields: Name (`<input type="text">`, required, maxlength 100), Email Address (`<input type="email">`, required), Phone Number (`<input type="tel">`, optional, maxlength 20); each field SHALL have a visible `<label>`.
5. WHEN a Customer submits the pre-chat form with a non-empty Name and an Email value matching the RFC 5322 simplified pattern `^\S+@\S+\.\S+$`, THE System SHALL store the submission in localStorage under `jrs-chat-leads` as a JSON array entry `{ name, email, phone, timestamp }` and display the confirmation "Thank you! Our support team will be in touch shortly."
6. WHEN a Customer submits the pre-chat form with a missing Name or an Email that does not match `^\S+@\S+\.\S+$`, THE System SHALL display a visible error message beneath the invalid field(s) (e.g., "Name is required" or "Please enter a valid email address") and SHALL NOT submit the form or record any data.
7. WHEN the floating chat button is clicked while the panel is closed, THE panel SHALL become visible; WHEN the button is clicked while the panel is open, THE panel SHALL close; WHEN a click is detected outside the panel's DOM boundary while the panel is open, THE panel SHALL close; WHEN the Escape key is pressed while the panel is open, THE panel SHALL close.
8. ON viewports with `window.innerWidth < 768`, THE Live_Chat_Widget panel SHALL render with `width: 100vw; left: 0; right: 0; bottom: 0` (full-width bottom sheet) such that no content from the page is obscured by the fixed-position floating button overlapping the panel.

### Requirement 7: Search Functionality

**User Story:** As a Customer, I want to search for perfumes by name or brand so that I can quickly find specific products.

#### Acceptance Criteria

1. THE Navbar SHALL include a search input that, WHEN clicked on desktop (viewport ≥ 768 px), expands inline to a minimum width of 240 px with a transition animation; on mobile (viewport < 768 px) it SHALL render as a full-width input below the logo row.
2. WHILE a Customer has typed at least 2 characters into the search field (after a debounce of 300 ms), THE System SHALL display a dropdown list of up to 8 products whose `name` or `brand` contains the query string as a case-insensitive substring match, sourced from the `PRODUCTS` array in `src/data/products.js`.
3. WHEN a Customer clicks a product in the search dropdown, THE System SHALL navigate to `/product/[slug]` for that product and THE dropdown SHALL close.
4. WHEN a Customer presses the Enter key while the search field is focused, THE System SHALL navigate to `/shop?q=[query]` and THE dropdown SHALL close.
5. WHEN the Shop page mounts or the URL `q` parameter changes, THE System SHALL apply the `q` value as an additional text filter ANDed with any active category, brand, fragrance type, and price filters already in the filter state.
6. IF the search query (typed in the Navbar or passed via the `q` URL parameter) produces zero matching products after filtering, THEN THE System SHALL display the message "No products found for '[query]'" and a `<Link to="/shop">` labelled "Browse all fragrances".
7. IF the Customer clicks outside the search dropdown's DOM boundary while the dropdown is open, THEN THE dropdown SHALL close and the input value SHALL be preserved.
8. IF the Customer presses the Escape key while the search dropdown is open, THEN THE dropdown SHALL close and the input field SHALL be cleared.

### Requirement 8: Recently Viewed Products

**User Story:** As a Customer, I want to see products I recently viewed so that I can easily return to items I was considering.

#### Acceptance Criteria

1. THE Frontend SHALL maintain a recently viewed list in localStorage under the key `jrs-recently-viewed` as a JSON array of product ID strings, capped at 10 entries, ordered by most-recently-viewed first.
2. WHEN a Customer's browser renders a ProductDetail page, THE System SHALL insert the current product's `id` at index 0 of the `jrs-recently-viewed` array; IF the `id` already exists anywhere in the array, THE System SHALL remove the existing entry before inserting at index 0; IF the array length would exceed 10 after insertion, THE System SHALL remove the last entry.
3. IF the `jrs-recently-viewed` array contains at least 2 entries (meaning at least one entry other than the current product), THEN THE ProductDetail page SHALL render a "Recently Viewed" section below the Related Products section showing up to 4 products (excluding the current product) resolved by matching IDs against the `PRODUCTS` array, rendered as `ProductCard` components.
4. IF the `jrs-recently-viewed` array is empty, or all entries match only the currently viewed product's ID, THEN THE System SHALL not render the "Recently Viewed" section.

### Requirement 9: Newsletter Subscription

**User Story:** As a Customer, I want to subscribe to the newsletter so that I receive updates about new fragrances and promotions.

#### Acceptance Criteria

1. THE Footer SHALL include a newsletter subscription form with an `<input type="email">` field and a "Subscribe" `<button>`.
2. WHEN a Customer submits the newsletter form with an email value matching the pattern `^\S+@\S+\.\S+$`, THE Backend SHALL upsert the subscription (insert if new, no-op if duplicate) into a `Newsletter` collection and return HTTP 200 with `{ success: true }`.
3. WHEN a Customer submits the newsletter form with an email that does not match `^\S+@\S+\.\S+$`, THE System SHALL display the error message "Please enter a valid email address." beneath the email input field and SHALL NOT make a network request.
4. WHEN the Backend returns `{ success: true }` (for both new and duplicate subscriptions), THE System SHALL display the message "Thank you for subscribing!" and clear the email input field value.
5. IF the Backend returns an HTTP 4xx or 5xx error, THEN THE System SHALL display "Something went wrong. Please try again." beneath the form without clearing the email input.

### Requirement 10: Trust Badges and Secure Payment Icons

**User Story:** As a Customer, I want to see trust indicators so that I feel confident purchasing from the site.

#### Acceptance Criteria

1. THE ProductDetail page SHALL render a trust badge row below the "Add to Cart" and "Buy Now" buttons containing exactly these four badges, each with a Lucide React icon and label: `ShieldCheck` + "100% Authentic", `Lock` + "Secure Payment", `RotateCcw` + "Free Returns", `Zap` + "Fast Shipping".
2. THE Cart page and Checkout page SHALL each render a payment methods row containing text or SVG labels for: Razorpay, Visa, Mastercard, and UPI; this row SHALL be visually distinct from the order summary content.
3. THE Footer SHALL render a trust row containing exactly these three badges, each with a Lucide React icon and label: `Lock` + "SSL Secured", `ShieldCheck` + "100% Authentic Products", `RotateCcw` + "Easy Returns".
4. All Trust_Badge icon and label colours SHALL use the Luxury_Theme CSS custom properties (`--color-luxury-gold` or `--color-rose-gold`) rather than hardcoded hex values, ensuring visual consistency with the overall theme.

### Requirement 11: Informational Pages — FAQ, Contact Us, Shipping & Returns

**User Story:** As a Customer, I want to access clear policy and contact information so that I can make informed decisions and reach support easily.

#### Acceptance Criteria

1. THE System SHALL provide a `/faq` route rendering an FAQ page with a minimum of 8 question/answer pairs, each pair rendered as an accordion item that expands and collapses the answer on click; only the question is visible when collapsed.
2. THE System SHALL provide a `/contact` route rendering a Contact Us page with a form containing: Name (`<input>`, required), Email Address (`<input type="email">`, required), Subject (`<input>`, required), and Message (`<textarea>`, required, maxlength 2000).
3. WHEN a Customer submits the Contact Us form with all four fields populated and the email matching `^\S+@\S+\.\S+$`, THE Backend SHALL persist the enquiry to a `ContactEnquiry` collection and return HTTP 200; THE Frontend SHALL then display "Your message has been sent. We'll get back to you within 24 hours." and reset all form fields.
4. WHEN a Customer submits the Contact Us form with any required field empty or the email invalid, THE System SHALL display a field-level error message beneath each invalid field (e.g., "Name is required", "Please enter a valid email address") and SHALL NOT submit the form.
5. THE System SHALL provide a `/shipping-returns` route rendering a static page with four clearly labelled sections: "Shipping Methods" (listing available carriers and estimated timeframes), "Delivery Timeframes" (standard and express), "Return Policy" (eligibility conditions and 15-day window), and "Refund Process" (steps and timeline).
6. THE Footer SHALL include `<Link>` elements to `/faq`, `/contact`, and `/shipping-returns` in the Help links column.
7. THE Navbar mobile drawer SHALL include `<Link>` elements to `/faq` and `/contact` in the mobile navigation list.

### Requirement 12: Premium Luxury Theme

**User Story:** As a Customer, I want the website to have a modern, premium look so that it feels trustworthy and luxury-aligned.

#### Acceptance Criteria

1. THE `src/index.css` file SHALL declare the following CSS custom properties in the `:root` selector: `--color-soft-black: #121212`, `--color-rose-gold: #B76E79`, `--color-ivory-white: #F8F4EE`, `--color-luxury-gold: #D4AF37`.
2. THE System SHALL apply the following glassmorphism CSS pattern to modal overlays, the Live_Chat_Widget panel, and the Navbar user/country dropdown menus: `background: rgba(255,255,255,0.08); backdrop-filter: blur(12px); border: 1px solid rgba(212,175,55,0.2)`.
3. THE ProductCard SHALL apply: `transform: scale(1.04)` on the image element on hover (200ms transition), a `background: rgba(212,175,55,0.15)` gold overlay div on hover, and an action bar div that transitions from `translateY(100%)` to `translateY(0)` on hover (300ms ease-in-out).
4. All interactive elements (buttons, links, card wrappers) SHALL use `transition: all 300ms ease-in-out` (or the equivalent Tailwind class `transition-all duration-300 ease-in-out`) for hover and focus state changes; no interactive element SHALL use a transition duration shorter than 150 ms or longer than 500 ms.
5. THE System SHALL be fully functional and free of horizontal overflow, unreadable text truncation, and broken layouts at viewport widths of 320 px, 768 px, and 1280 px; this SHALL be verified by visual inspection at each breakpoint.
6. WHEN `Data_Saver_Store.enabled` is `false`, THE System SHALL render: `PageTransition` fade-up on route change, `Reveal` IntersectionObserver entrance animations, and `useSlideIn` card stagger animations.
7. THE `tailwind.config.js` SHALL extend the `theme.colors` object with keys `rose-gold: '#B76E79'`, `ivory: '#F8F4EE'`, `luxury-gold: '#D4AF37'`, and `soft-black: '#121212'` so they are available as Tailwind utility classes (e.g., `text-rose-gold`, `bg-luxury-gold`).

### Requirement 13: Enhanced Shopping Cart

**User Story:** As a Customer, I want a complete and clear shopping cart experience so that I can review, adjust, and proceed to checkout with confidence.

#### Acceptance Criteria

1. THE Cart page SHALL render each Cart_Item row containing: a product thumbnail `<img>`, product `name`, product `brand`, selected `size` label, unit `price`, a quantity stepper (minus button, count display, plus button), a line total (`price × quantity`), and an `<X>` remove button.
2. THE Cart page order summary section SHALL display: subtotal (sum of all line totals), shipping (₹0 if subtotal ≥ ₹3,000; otherwise ₹199), a tax display row labelled "GST (18%)" showing `Math.round(subtotal * 0.18)`, and a total row summing all three; these values SHALL update reactively as Cart_Store items change.
3. WHEN a Customer clicks the minus stepper button on a Cart_Item whose current quantity is 1, THE Cart_Store SHALL call `removeItem(productId, size)` removing that item from the cart; the Cart page SHALL re-render without the removed item.
4. THE Cart page SHALL render a "Proceed to Checkout" button; WHEN clicked by an Authenticated_User, it SHALL navigate to `/checkout`; WHEN clicked by a Guest, it SHALL navigate to `/login?returnTo=/checkout`.
5. THE Navbar SHALL read `Cart_Store.items.reduce((sum, i) => sum + i.quantity, 0)` and render the result as a badge on the cart icon; WHEN the count increases, the badge SHALL play the existing `scale-150` bump animation for 400 ms.
6. IF `Cart_Store.items` is an empty array, THEN THE Cart page SHALL display a "Your cart is empty" heading and a `<Link to="/shop">` labelled "Continue Shopping", with no Cart_Item rows or summary totals rendered.
7. THE Cart page SHALL render a payment methods row (as defined in Requirement 10, criterion 2) beneath the "Proceed to Checkout" button.

### Requirement 14: Related Products Section

**User Story:** As a Customer, I want to see related products on the product detail page so that I can discover other fragrances I might enjoy.

#### Acceptance Criteria

1. THE ProductDetail page SHALL render a "Related Fragrances" section containing up to 4 products from the `PRODUCTS` array that share the same `category` value as the viewed product, excluding the viewed product itself, ordered by descending `rating`.
2. IF fewer than 4 products share the same `category` (after excluding the current product), THEN THE System SHALL supplement with products sharing the same `fragranceType` (also excluding the current product and already-selected category matches) until the total reaches 4 or the combined pool is exhausted.
3. IF no products satisfy criterion 1 or 2 (pool is empty after exclusions), THEN THE System SHALL not render the "Related Fragrances" section element.
4. Each item in the "Related Fragrances" section SHALL be rendered as a `ProductCard` component, which includes the add-to-cart action and (with the new Wishlist feature) the heart/wishlist toggle.

### Requirement 15: Account Dashboard Enhancements

**User Story:** As an Authenticated_User, I want a comprehensive account dashboard so that I can manage my profile, addresses, and preferences in one place.

#### Acceptance Criteria

1. THE Account page SHALL include a "Saved Addresses" tab rendered alongside the existing Orders, Profile, and Refer & Earn tabs; the tab SHALL display all shipping addresses stored for the user, each with "Edit" and "Delete" action buttons, and an "Add New Address" button.
2. WHEN an Authenticated_User submits a new address form with required fields (fullName, line1, city, state, pincode, phone) populated, THE Backend SHALL persist an address sub-document on the User model linked to `req.user._id` and return the updated address list; THE Frontend SHALL render the new address in the list without a full page reload.
3. WHEN an Authenticated_User clicks "Delete" on a saved address, THE Backend SHALL remove the address sub-document and return HTTP 200; THE Frontend SHALL remove that address card from the list immediately (optimistic update with rollback on error).
4. THE Account page SHALL include a "Wishlist" tab whose content is identical to the `/wishlist` page (Wishlist_Store items rendered as ProductCard components with Move-to-Cart and Remove actions).
5. THE Account page "My Orders" tab SHALL render each order row with a "Track Order" `<Link>` that navigates to `/track-order?orderId=[orderNumber]`; THE Track Order page SHALL read the `orderId` URL parameter and pre-populate the Order ID input field on mount.
6. IF the Authenticated_User has no saved addresses, THEN THE Saved Addresses tab SHALL display the message "No saved addresses yet." and an "Add Your First Address" button that opens the address form.
